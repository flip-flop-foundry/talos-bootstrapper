# Talos Machine Configuration

## What it does

This component contains the Talos Linux machine configuration patches that are applied on top of the base Talos machine config generated by `talosctl`. These patches customise the cluster nodes with:

- **`talosPatchConfig.yaml`** — common patches applied to all nodes (NTP, sysctls, kubelet extra args, etc.)
- **`talosPatchConfigControlplane.yaml`** — additional patches for control-plane nodes only
- **`systemVolumes.yaml`** — STATE/EPHEMERAL encryption, merged into every node config during cluster setup
- **`secondHddVolume.yaml`** — example `UserVolumeConfig`; not wired into any task, disk auto-detection generates the real ones
- **`filesystemTrimConfig.yaml`** — scheduled `fstrim` of mounted filesystems (Talos 1.14+)
- **`securityProfileConfig.yaml`** — pins workload isolation (sandboxd) on or off (Talos 1.14+)
- **`trustedRootsConfigTemplate.yaml`** — distributes the cluster CA to Talos nodes so they trust internal services

## Filesystem Trim and Encrypted Volumes

Talos 1.14 can periodically run the equivalent of `fstrim` on mounted filesystems, which
returns unused blocks to the underlying device. This matters on SSDs and on thin-provisioned
storage, where blocks freed inside the guest are otherwise never reclaimed by the hypervisor
or SAN.

Two pieces are required, and both are Talos 1.14+ schema:

1. **`filesystemTrimConfig.yaml`** — a `FilesystemTrimConfig` document setting the global
   interval from `TALOS_FILESYSTEM_TRIM_INTERVAL` (default `168h0m0s`). Talos derives the
   actual trim time per node and per volume from a hash of both, so nodes do not all trim
   at the same moment.
2. **`encryption.allowDiscards: true`** — set on every encrypted volume in
   `systemVolumes.yaml` and on the `UserVolumeConfig` documents generated by disk
   auto-detection. Without it, TRIM requests stop at the LUKS layer and an encrypted
   volume is skipped by the trimmer entirely.

> **Security trade-off**: discard passthrough lets the backing device observe which blocks
> the filesystem considers free, revealing how much of the volume is in use and roughly
> where. This is the standard LUKS discard trade. If a cluster's threat model includes an
> untrusted hypervisor or SAN, remove `allowDiscards` and accept that encrypted volumes are
> never trimmed.

### Version requirement

Both are Talos 1.14+ schema. `cluster-initialSetup.sh` refuses to run unless `TALOS_VERSION`
(the config contract) and the local `talosctl` are both v1.14.0 or newer, so there is no
fallback for older contracts.

`allowDiscards` changes how the LUKS device is opened, so it takes effect on the next boot
of the node rather than immediately on apply.

## Workload Isolation (sandboxd)

Talos 1.14 can run the container runtime plane — CRI containerd, the kubelet, and every pod —
inside a dedicated PID and mount namespace anchored by the `sandboxd` service, isolating it
from `machined` (PID 1). It is controlled by the `SecurityProfileConfig` document.

The default is inconsistent, which is one reason this repo pins it off:

| Cluster | Default |
|---------|---------|
| Freshly generated at contract 1.14+ | `talosctl gen config` emits the document with `workloadIsolation: true` |
| Upgraded from 1.13 or earlier | document absent, which Talos reads as isolation off |

`securityProfileConfig.yaml` sets `workloadIsolation: false` on every node. It is not
configurable, because every cluster built from this repo runs Longhorn (see below). Talos treats an
explicit `false` exactly like an absent document — sandboxd is enabled only when the document
is present *and* the field is true — so pinning it is a no-op on an upgraded cluster and only
changes behaviour for a newly generated one.

Because `gen config` already emits this document at contract 1.14+, `securityProfileConfig.yaml`
is merged (not appended) into every node config: the strategic merge matches the singleton
by kind and overrides `workloadIsolation`, so no duplicate document is produced.

### Why it is off

The breakage Talos documents explicitly is the **deprecated in-tree Kubernetes iSCSI volume
plugin**: under isolation the kubelet cannot reach the host `iscsid`. Longhorn is a CSI driver,
so that specific warning does not apply to it — but Longhorn's own host access is not obviously
safe either, which is why this stays off until someone measures it.

Longhorn does not talk to the host through PID 1. On Talos it resolves namespaces *by process
name*: `go-common-libs` maps the Talos OS distro to the `kubelet` process for its default
namespace target, and the startup iSCSI check enters the namespaces of the process named
`iscsid`, located by scanning `/host/proc`. Volume encryption (`cryptsetup`) instead uses the
host namespace helper, which walks up to `containerd`/`containerd-shim` and falls back to PID 1.

Two things make this hard to reason about without testing:

- All three lookups predate `sandboxd`. Under isolation the kubelet and containerd move inside
  the sandbox while `iscsid` (the `siderolabs/iscsi-tools` extension service) stays outside it.
- The process lookup **falls back to the host namespace PID when the named process is not
  found**, so a failure to locate `iscsid` does not raise an error — it silently runs the
  command in a different namespace.

There is no upstream Longhorn issue covering Talos workload isolation either way, so treat
`true` as unverified for a Longhorn cluster: test it on a single worker first, confirm a volume
attaches and a replica rebuilds, then roll it out. A per-node file under `talos/nodes/` cannot
do this (see [Per-Node Patches](#per-node-patches)); patch the one node directly instead,
e.g. `talosctl patch machineconfig --nodes <worker> --patch @<file>` with a
`SecurityProfileConfig` setting `workloadIsolation: true`, and reboot it. The next
"Apply Talos configs" run reverts that node; enabling it cluster-wide means changing
`securityProfileConfig.yaml`.

Also note that workload isolation is still settling upstream.
[talos#14374](https://github.com/siderolabs/talos/issues/14374) (CRI restart-looping every boot
under isolation) was fixed by [#14392](https://github.com/siderolabs/talos/pull/14392), which
landed *after* v1.14.1 — v1.14.1 carries a different sandboxd fix. Check that your Talos version
actually contains the fix before enabling this.

## Per-Node Patches

Individual nodes can have their talos machineconfig customised by placing a YAML patch file in the overlay:

```
overlays/<cluster>/talos/nodes/<hostname>.yaml
```

The hostname is the short name (first label of the FQDN, e.g. `brew-10` for `brew-10.example.com`).

These patches are merged with Talos' strategic merge (documents matched by kind + name) **after** all role-level patches, but **before** disk detection and the all-node manifests (`systemVolumes.yaml`, `filesystemTrimConfig.yaml`, `securityProfileConfig.yaml`). Settings in those manifests therefore win over a per-node patch.

Example — disable hugepages on a memory-constrained Raspberry Pi node:

```yaml
# overlays/${SOME_OVERLAY}//talos/nodes/brew-10.yaml
machine:
  sysctls:
    vm.nr_hugepages: "0"
```

## Why it was added

Talos Linux requires machine configuration to be provided at boot time. This component holds the overlay-agnostic base patches. Cluster-specific machine configs are generated by the "Apply Talos configs" VS Code task (`cluster-initialSetup.sh` in the devenv workspace) and stored in `$TALOS_BOOTSTRAPPER_DATA_DIR/environments/<env>/talos/`.

The **installer image** embedded in the machine config is derived from three `.env` variables:
- `TALOS_INSTALL_VERSION` — e.g. `v1.12.4`
- `TALOS_INSTALLER_TYPE` — platform + Secure Boot variant (see table below)
- `TALOS_SCHEMATIC_EXTENSIONS` + `TALOS_SCHEMATIC_EXTRA_KERNEL_ARGS` — baked into the schematic

| Installer Type | Platform | Typical Hardware |
|----------------|----------|-----------------|
| `metal-installer-secureboot` | `metal` | Bare metal, modern UEFI + Secure Boot |
| `installer-secureboot` | `metal` | Bare metal, UEFI Secure Boot (older) |
| `installer` | `metal` | Bare metal, no Secure Boot |
| `nocloud-installer-secureboot` | `nocloud` | Proxmox VMs, cloud hypervisors |

For Raspberry Pi 4, a separate `rpi_generic` SD card image is generated by the "Setup PXE Server" VS Code task (`pxe-setup.sh` in the devenv workspace) — see the Node Provisioning section in the top-level README.

## Dependencies

None — this component contains static configuration templates that are consumed by the "Render Overlay" VS Code task (`render-overlay.sh` in the devenv workspace) and `talosctl` during cluster setup.

## Dependents

None — the generated Talos machine configs in `overlays/<cluster>/talos/` are consumed directly by `talosctl`, not by other Kubernetes components.

## User Guide

### Applying a configuration change to nodes

1. Edit the relevant patch file in `base/talos/`, in `overlays/<cluster>/talos/`, or in `overlays/<cluster>/talos/nodes/<hostname>.yaml` for a single node.
2. Re-render via the "Render Overlay" VS Code task (or run `render-overlay.sh` from the devenv workspace).
3. Apply the updated config to the nodes:
   ```bash
   talosctl apply-config --nodes <node-ip> --file $env/_rendered/talos/<node>.yaml
   ```

### Upgrading Talos

Update `TALOS_INSTALL_VERSION` in the overlay `.env` file, then:

```bash
talosctl upgrade --nodes <node-ip> --image factory.talos.dev/installer/<schematic-id>:<version>
```

### Upgrading Kubernetes

Update `KUBERNETES_VERSION` in the overlay `.env` file, then:

```bash
talosctl upgrade-k8s --to <version>
```
